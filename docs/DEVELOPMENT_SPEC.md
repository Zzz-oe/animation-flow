# 开发 Spec：ScenePilot 动画分镜 AI 协作编辑器

状态：核心 Demo 已完成；阶段 5 的真实评审和真实候选边界已验证，阶段 6 进行交付收尾。真实图像候选保持隔离，接受后才覆盖舞台；结构化图层映射仍是已知边界。

开发前先读 `EVALUATION.md`。本 Spec 是需求到实现的逐步拆解；阶段顺序可根据技术验证调整，但不得削弱验收基线。

## 1. 产品问题与原则

分镜创作需要持续判断构图、叙事焦点、动作可读性和情绪传达。普通生成式工具常在“给意见”与“直接重做”之间缺少可控协作。本产品让 AI 理解当前画面与创作意图，提供带依据的建议，并在用户授权后产出可比较的修正版。

原则：

- 人拥有最终决定权；默认不覆盖。
- 每个 AI 结果都可解释、可追溯，并尽量绑定场景元素或区域。
- 场景上下文驱动评审和生成提示词。
- Mock 优先保证体验，真实模型作为可切换能力。
- 只实现支撑闭环所需的编辑器功能。

## 2. 主要用户旅程

1. 用户打开工作区，选择模板/示例场景或新建场景。
2. 用户调整场景元素，并填写镜头目标、叙事意图、风格等上下文。
3. 用户请求 AI 评审，看到加载状态及评审报告。
4. 用户查看具体建议与依据，选择建议、改写要求或排除不想改动的区域。
5. 用户请求生成修正版，看到候选方案，而非被替换的原稿。
6. 用户比较候选与原稿，接受、拒绝、恢复或基于结果再次迭代。
7. 用户查看操作历史并导出/分享结果。

## 3. 功能需求

### F1 工作区与示例

- 提供完整的初始动画分镜场景，首次进入即可开展评审和修改。
- 提供清晰的新建/重置/切换案例路径。
- 案例应代表不同工作流问题，例如构图焦点、遮挡关系、动作可读性；案例数量在实现阶段按时间确定。

### F2 Canvas 编辑

- 呈现明确舞台边界、背景及场景对象。
- 对场景对象执行选择和基础变换；对象信息可在图层/属性面板查看。
- 支持基本增删、排序、显隐或锁定。取舍以可靠演示为准。
- 保存必要场景状态，避免 AI 请求造成未提交编辑丢失。

### F3 创作上下文

每个场景至少有可编辑的自然语言创作目标；建议另包含镜头类型、情绪、视觉风格、不可更改约束。上下文随评审和生成请求传递。

### F4 评审服务

输入：画面/画布快照、结构化场景对象（如可用）、创作目标、风格和限制、模式配置。

输出建议 schema：

```ts
type ReviewResult = {
  summary: string;
  overallScore?: number;
  dimensions: Array<{
    name: string;
    score?: number;
    observation: string;
  }>;
  findings: Array<{
    id: string;
    severity: "high" | "medium" | "low";
    category: string;
    title: string;
    evidence: string;
    targetIds?: string[];
    region?: { x: number; y: number; width: number; height: number };
    recommendation: string;
    expectedEffect: string;
  }>;
};
```

实际实现应运行时校验响应，不信任模型输出。界面需展示加载、成功、无问题、错误和重试状态。

### F5 建议决策与生成修正

- 每条 finding 可单独选择；可补充用户指令和保护约束。
- 生成请求使用当前画面、原始创作目标、所选建议和保留项构造 Prompt。
- 输出成为 candidate revision，带版本/请求元数据；不得静默写入当前稿。
- 失败或取消不能破坏原稿。

### F6 对比、版本和历史

- 可以清楚对比当前版本与候选版本。
- 接受候选、拒绝候选或恢复之前版本。
- 历史项至少记录动作、时间/顺序、简要结果；真实或 Mock 模式应可区分。

### F7 Provider 架构

- 定义 `review` 与 `generateRevision` 的 provider 接口。
- Mock provider 确保无凭据完整工作且响应确定性高。
- 真实 provider 经服务端边界调用；浏览器不持有服务密钥。
- 配置缺失、速率限制、超时、无效结构均可理解地降级/报错。

### F8 交付与说明

- 可部署的公网体验或公开源码仓库。
- README/交付说明涵盖题目要求的实现、规划、人机交互、工具、Token 与个人耗时。
- 开发日志记录实际事实；不确定 Token 应注明来源或估算方法。
- 记录一个或多个真实失败/局限及原因，不杜撰失败经历。

## 4. 非功能需求

- 桌面主工作区清晰，窄屏至少可以完成核心流程。
- 键盘焦点、语义标签、对比度和状态反馈达到基本可访问性。
- Canvas 渲染和 AI 请求分离；请求中防止重复提交。
- 用户画面状态在请求失败、取消和重新生成时保留。
- 初次启动和部署步骤可复现；无秘密材料进入仓库。
- 建立针对 schema、交互状态和关键用户旅程的测试。

## 5. 建议架构

- React + TypeScript + Vite（若现有项目技术栈适合则遵从现状）。
- Konva/Fabric 等成熟 Canvas 库择一，避免自行从头实现对象变换。
- 状态模型区分 `scene`、`review`、`candidate revision`、`history`。
- Provider 层隔离 Mock/真实模型；请求数据集中构造并可记录（脱敏）。
- 将 Canvas 快照、对象元数据、Prompt 模板和结构化响应校验作为独立模块。
- 具体库及部署目标在项目骨架检查后确认。

## 7. 评测方案

- 为至少若干代表场景准备预期问题/建议和不可修改约束。
- 评审质量：相关性、依据具体性、可执行性、动画工作流适配度、约束遵循。
- 人机体验：用户能否辨认建议目标、控制执行范围、比较并撤销结果。
- 生成质量：任务遵循、角色/风格保持、非目标区域保持、结果可用性。
- Mock 的作用是验证交互，不应伪称验证模型能力。
- 真实模型若接入，记录案例、失败、人工判定标准；评分不是只报单一总分。

## 8. 风险与缓解

- 范围蔓延：优先完整协作闭环，编辑器功能按需。
- API/模型不可用：Mock 保底，失败状态清晰。
- 角色一致性和局部编辑失败：候选隔离、对比、拒绝/恢复，并记录局限。
- 模型输出不可控：schema 校验、边界提示和人工确认。
- 过度声称能力：区分 Mock 与真实模式，README 记录证据。
- 凭据泄露：只在服务端保存/读取密钥。

## 9. 决策记录

- 初始方向采用动画分镜协作编辑器。
- Mock 为默认保底，真实模型集成为加分阶段。
- 具体实现依赖、测试策略与部署目标待阶段 0 确认。
- 阶段 3 以 provider 接口隔离 Mock 与未来真实模型；UI 不直接依赖某个模型响应实现。
- 评审结果绑定场景指纹。编辑画面或导演意图不会删除旧结论，但会显式标记过期，兼顾比较与决策安全。
