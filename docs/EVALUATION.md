# 评测基线：动画 AI 编辑器笔试

本文件是项目开发与验收的最高优先级产品基线。每次开发前必须通读，并以此检查范围和结果。题目截图中的要求与我们的实现建议应区分：前者是考题要求，后者是为争取高质量交付制定的方案。

## 考题原始要求

题目 B「动画 AI 编辑器方向」要求设计一个与多模态 LLM、图像生成 AI 交互作画的编辑器：调用多模态 LLM 评价人的编辑结果，调用图像生成 AI 生成内容，并修正人的编辑结果。

题目明确强调：

- 侧重人机交互逻辑与绘画工作流设计。
- 不侧重编辑器功能实现或性能优化，基础 Canvas 即可。
- 不强求真实接入 LLM/AI 生成功能，允许 Mock。
- 加分项：真实接入 LLM 评估和图像生成。
- 加分项：由绘画工作流驱动的场景细化与 Prompt 特调。

交付物：

1. 一个公网可访问 URL，或者公开 GitHub 源码仓库。
2. 一份 Markdown 简要说明，覆盖实现方式及时间规划、人和 AI Agent 交互设计的考虑与侧重点、使用的 AI Coding 工具及大致 Token 用量（含最耗 Token 的部分）、本人耗时最多的部分（不计 LLM 直接完成的工作）。

## 产品目标

交付一个可运行、可演示、可审阅的动画分镜 AI 协作编辑器。核心价值不是“AI 一键出图”，而是让动画创作者能在保留控制权的前提下，利用 AI 评估画面、选择建议并生成可比较、可接受或可拒绝的修正版本。

暂定产品概念：ScenePilot（名称可在后续品牌设计阶段调整）。目标用户为动画分镜师、概念设计师或动画创作者。

## 核心验收闭环

```text
建立场景 → 人工编辑 → 提供创作意图 → AI 多模态评审
→ 展示带依据的问题与建议 → 用户选择/调整建议
→ AI 生成修正版 → 前后对比 → 接受/拒绝/恢复/继续迭代
```

AI 不得静默覆盖用户作品。用户应能理解建议、限定修改范围，并决定是否应用结果。Mock 模式必须无凭据可完成完整演示；真实模型接入不能成为核心流程的单点故障。

## 产品能力基线

### 基础 Canvas

- 显示舞台/画布和场景元素。
- 添加或导入背景、角色、道具、文字等基本元素。
- 选择、移动、缩放、旋转元素；支持基本图层排序、隐藏、锁定和删除。
- 有可理解的属性/图层区域与基本撤销恢复能力。
- 能展示、导出或分享场景结果。

Canvas 是工作流承载界面，不追求专业绘图软件的完整功能。具体功能可基于核心演示需要裁剪。

### AI 生成

- 根据动画场景意图、镜头、角色状态、风格等信息生成候选内容。
- 候选结果与当前作品分离，不直接覆盖。
- 支持接受、拒绝或再次生成；可在可行时限定需修改的目标/范围。

### 多模态 AI 评审

评审应面向动画绘画场景并尽可能结构化，可覆盖构图、视觉焦点、遮挡、空间关系、动作可读性、情绪表达、风格一致性等。输出应包含问题、严重程度、依据/位置、可执行的修改建议和预期效果，而不只给泛化文字。

### AI 修正与过程透明度

- 先由 AI 提议，再由用户选择/编辑，之后才生成修正。
- 展示原版与候选修正版的差异或对比。
- 支持接受、拒绝、恢复原版；保留关键操作记录。

### 双模式与韧性

- Mock 模式开箱即用，结果稳定、可重复、可演示。
- 可选真实模型模式；密钥不得暴露在浏览器端，应使用安全服务端代理或等效方案。
- API 不可用、超时或返回异常时给出清楚状态，用户仍可继续演示核心流程。

## 质量与评分策略

优先级：

1. 动画创作场景具体且可信。
2. 人机协作控制权清晰、流程完整、行为可解释。
3. 评审输出有依据、可定位、可执行；生成 Prompt 由工作流上下文驱动。
4. 作品可用、视觉完成度高、演示路径稳定。
5. 真实模型集成作为加分项，在可靠性和时间允许时完成。
6. Canvas 高级工具和性能优化最后考虑。

推荐准备几个有代表性的内置场景/体验案例、架构与 Prompt 说明、可复现评测、失败案例和演示素材。只在实际完成后才作为交付事实陈述。

## 验收检查

- 新用户能否无需说明就找到并完成核心闭环？
- Mock 模式是否不用 API Key 就能跑通？
- AI 建议是否与具体动画任务和当前画面相关，而非套话？
- 用户能否选择、拒绝、比较、恢复 AI 修改？
- 错误、等待、空状态是否清楚，是否会丢失用户内容？
- 交付 URL/仓库及 Markdown 说明是否齐全？
- Token、时间、测试、真实接入和部署陈述是否有依据？

## 范围边界

不以复杂绘图工具、专业级图层系统、协作编辑、像素级图像处理或未经验证的模型效果为目标。任何扩展应证明它改善了动画工作流或核心交付质量。
